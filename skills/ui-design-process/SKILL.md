# UI/UX 設計の進め方

依頼の言葉をそのまま形にしない。言われた「ほしい物」の奥にある、まだ言葉になっていない目的まで降りてから作る。良し悪しは見た目の好みではなく、そのプロダクトで使う人が目的を終えられるかで決める。

各段は薄く、検証だけを厚くする。段ごとに「決めたと言える形」があり、それが書けないうちは次の段へ進まない。決めたことは設計メモに1行ずつ残す。原則の名前ではなく、採った判断を書く（「Hick の法則を適用」ではなく「選択肢を7つから3つに絞り、残りは詳細設定へ送った」）。

## 1. 狙いを決める

次の4つを埋めるまで、1px も作らない。

| 欄 | 決まった形 | まだ決まっていない形 |
|---|---|---|
| 使う人 | 使う瞬間の様子。時間の余裕・気持ち・手の状態・場所。例：「訪問の直後、片手にスマホ、1時間以内に記録しないと同期されない」 | 「35歳の営業職」「会社員」（属性であって、使う瞬間ではない） |
| 主な行動 | 1つだけ。例：「訪問の記録を素早く残して同期する」 | 4つ並ぶ。それは画面を分ける合図 |
| 賭け | 「〇〇すれば△△になるはず」という確かめられる仮説 | 「使いやすくする」（確かめられない） |
| 制約 | 画面の幅・既存のデザインシステム・API・法務・期日を具体的に | 「特になし」 |

あわせて次を確かめる。

- 使う人の最終的な目的は何か。作業（「フォームを送る」）ではなく、終えたときの状態（「今日の記録を残し終えて安心する」）
- このプロダクトはどう使われるか。一日中開いている道具なら密度を上げて慣れに合わせる。たまに来る画面なら説明を厚くして迷わせない。裏で動く物なら存在を意識させない

**決めたと言える形**：設計メモの冒頭に1行。
> 完了＝〇〇。この画面で使う人に起きてほしいのは△△。賭け＝〜すれば〜になるはず。

## 2. 文脈をつかむ

新しく描く前に、今ある物を見る。順番は、既存の実装 → 要件 → これまでの決定 → デザインシステム。

使う人がどう探しに来るかを決める。主な探し方で、置く仕組みが変わる。

| 探し方 | 例 | 効く仕組み |
|---|---|---|
| 名前を知っている物を探す | 「あの契約書」 | 検索、五十音・日付などの決まった並び |
| 何があるかを見て回る | 「リモートで使える道具」 | 一覧を見て回る導線、話題での分類、関連の導線 |
| 漏れなく集める | 「この件の全部」 | 絞り込みの条件（ファセット） |
| 前に見た物に戻る | 「この前のやつ」 | 履歴、ブックマーク、変わらない URL |

探している途中で、問いそのものが変わる。途中で向きを変えられる手がかり（関連・絞り込み・「こちらも」）を置く。検索だけ、一覧だけの片方では落ちる。

使う人のふるまいとぶつかっていないかも見る。

- 取り消せると思えるときだけ、人は試す。戻る・取り消しの無い画面では、知っている操作しか使われない
- 人は一番いい物を探さず、最初にそれらしく見えた物を押す。大事な選択肢は最初に目に入る場所に置く
- 途中で中断して戻ってくる。どこまでやったかを残し、一目で分かるようにする
- 今答えられない質問は飛ばしたい。全部が必須の入力は離脱の場所になる
- 位置で覚える。大事な物の場所を画面ごとに変えない

**決めたと言える形**：「主な探し方は〈見て回る〉。だから話題で分け、関連の導線を置く」のように、選んだ物と構造への効き方を1〜2行。

## 3. 構造を作る

画面の一覧から始めない。使う人が扱う「物」の一覧から始める。

1. **物を取り出す。** 要件・会話・既存の画面の言葉から名詞を集め、使う人の関心の対象だけに絞る（セッション・トランザクションなどシステムの都合は落とす）。物と言える条件は3つで、名前で呼べる・数えられる・状態とふるまいを持つ
2. **関係を決める。** 1対多・参照・主従
3. **見せ方を決める。** 主な物ごとに「一覧」と「詳細」の2つの見せ方を基本にする。作成・編集・削除は、新しい画面ではなく、その見せ方の中の操作にたたむ

ナビゲーションの項目が動詞（「レポートを作成する」）ばかりなら、作業ごとに画面が増えている合図。手順が厳密に決まっていて、対象が最初は存在しない場合（申込など）だけ、作業の順に並べる形を選ぶ。

分類とラベル：

- 階層は広く浅く。最上位に30項目は多すぎ、6階層を超えると迷う
- 1つの物を複数の分類に置いてよい。使う人は自分の考え方で探しに来る
- ラベルは作らず拾う。既存の文書・検索の記録・使う人が実際に使う言葉から取る
- 同じ並びに、粒度の違う物（「機器」と「USB ケーブル」）や、品詞の違う物を混ぜない
- アイコンだけで意味が通るのはごく一部。文字を添える

**決めたと言える形**：物の表（名前・持つ情報・できる操作・関係）と、見せ方の一覧。

## 4. 画面を作る

先に既存のデザインシステムの部品で組めないかを見る。手で作るのは最後の手段で、作るならデザインシステムに足してから使う。

この画面の役割を1つに決める。役割が混ざると焦点が散る。

- 1つの物を見せる：中身が主役。ナビゲーションと道具は脇
- 物の一覧を見せる：並べ替え・絞り込み・詳細への導線
- 物を作る道具：作業の場所と道具。道具は常に手の届く場所
- 1つの作業を終えさせる：今どこか・あと何があるかを示し、完了までの道をはっきりさせる。飛ばす・戻る・途中で保存するを許す

並べ方を決めるときに当てる経験則：

- 大事なボタンは大きく、手の近くに置く。タッチは 44×44px 以上
- 一度に見せる選択肢を絞る。迷ったら賢い初期値を入れる
- 長い入力は意味のまとまりで区切る
- 慣れた配置に従う。新しさは中身で出し、枠組みは慣例どおりにする
- よく使う2割の機能を一番近くに置き、残りは奥に置く
- 強調は1つ。周りと違う物だけが目に残る
- まとまりは近さと揃えで作る。飾りで階層を作らない

ふるまいを決めるときの問い：

- この操作は、使う人の目的に必要か。手続きのためだけの操作なら消す
- 本当にモーダルで止める必要があるか
- よく起きることと、起きうることを分けたか。まれな場合を主な道に混ぜていないか
- 確認を求める前に、実行させて取り消せるようにできないか
- 最初の画面が真っ白で始まっていないか
- 途中までの入力・あいまいな入力を受け付けるか

入力の部品の既定：

| 入力 | 既定の部品 |
|---|---|
| はい・いいえ | チェックボックス、トグル |
| 2〜5の中から1つ | ラジオボタン（全部が見える） |
| 6以上の中から1つ | セレクト、候補付きの入力 |
| 複数を選ぶ | チェックボックスの並び |
| 短い文・長い文 | 1行の入力欄・複数行の入力欄 |
| 数 | 範囲ならスライダー、正確さが要るならステッパーか入力欄 |
| 日付 | カレンダー、または形式の例を添えた入力欄 |

**決めたと言える形**：画面の役割・使った部品・最適化した相手（初めての人か、慣れた人か）を1行。

## 5. 細部を詰める

操作できる要素1つずつに、12の状態（送信の仕方・キーボード・タッチ・読み込み中・結果が0件・エラー・無効・最初の空・入力中・フォーカス・hover・支援技術）を決める。内容は ui-review スキルの「状態が全部あるか」と同じ表を使う。空欄が1つでもあれば出さない。

言葉：

- 画面の見出しとボタンの語をそろえる
- ボタンは短い動詞で始める
- 最初の空の状態は、事故ではなく招待として書く。最小の形は「〇〇するには、△△しましょう」
- エラーは原因と次の一手を書き、責めない
- 説明文は短く。読まなくても終えられる作りにする
- 日付・金額・件数は、0・マイナス・桁あふれ・長い文字まで決めておく

AI が結果を作る画面なら、出所・確かさ・生成中の見せ方・一部だけ直す道の4つを、この段で決める。

**決めたと言える形**：要素ごとの12の状態の表（空欄なし）と、確定した文言。

## 6. 検証する

1. 描画して、自分の目でスクリーンショットを見る。見ていない物は合格にしない
2. 幅を変えて見る（スマホ・タブレット・PC）
3. 画面の字を1つずつ読み、「使う人はこれを読んで次に何をするか」が言えるか確かめる。言えない字は消す
4. ui-review スキルで、致命がゼロになるまで直す。自分で作った物は、作った文脈を切り離して見る

## 受け渡すとき

設計メモに次を残す。

- 狙いの1行
- 段ごとに採った判断（なぜそうしたかを、使う人の場面で書く）
- 状態の表
- 自分で見つけて直した欠陥
- 決めきれなかったことと、その理由

## 避けること

- 狙いが書けないまま描き始める
- 既存のデザインシステムを見ずに部品を新しく作る
- 画面名から設計を始める
- 正常な状態だけを作って出す
- 流行だけを理由に選ぶ。依頼者の言う通りにするだけで、目的を損なう要求に理由と代わりの案を出さない
