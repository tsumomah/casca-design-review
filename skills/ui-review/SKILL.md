# UI/UX レビュー

目的は1つ。作った人の思い込みの外から、使う人が困る欠陥を見つけること。褒める欄は無い。良い所を挙げるのは、直さないと決めた理由を説明するときだけにする。

## 進め方

1. **実物を見る。** 画面なら描画して自分の目で見る。コードしか無ければ、ブラウザやプレビューで描画できるか先に試す。描画できないときは「描画せずコードから読んだ」と結果の先頭に書き、見た目の判定を「未確認」として分ける。見ていない物を合格にしない
2. **狙いを1行にする。** 「この画面で、誰が、何を終えられたら成功か」。書けなければ、それ自体を最初の致命として返す。狙いが分からないと、どの欠陥が重いかを決められないから
3. **画面ごとに下の観点を通す。** 別の画面の結果で代用しない
4. **欠陥を3つに分ける。**
   - 致命：使う人が目的を終えられない、誤る、データを失う、読めない・操作できない人がいる
   - 改善：終えられるが遅い・迷う・不安になる
   - 好み：直さなくても成立する
5. **返す。** 形は末尾の「出力の形」。致命が1件でも残っていれば「合格」と書かない

自分が作った物を自分でレビューするときは、作った文脈を切り離す。サブエージェントや別の会話が使えるなら、このファイルと対象だけを渡して見てもらう。

## 観点

### 1. 目的に届くか

- 狙いの行動まで最短か。行き止まり・戻れない分岐・同じ入力の繰り返しが無いか
- 道具の都合（データベースの形・API の単位・作りやすさ）が、使う人の手順に漏れていないか。例：内部の ID を入力させる、保存の単位が使う人の区切りと違う
- 押せる物が押せると分かるか。押せない物が押せそうに見えていないか

### 2. 状態が全部あるか

正常に表示された状態だけの画面は未完成として扱う。操作できる要素1つずつに、次の12の状態があるかを確かめる。順番が大事で、正常系から考えると後半まで届かない。

| 順 | 状態 | 見ること |
|---|---|---|
| 1 | 送信の仕方 | Enter・ボタン・両方のどれか。実行の手段が見えているか |
| 2 | キーボード | 日本語 IME の変換確定の Enter で誤って送信しないか。Tab の順が見た目の順と同じか |
| 3 | タッチ | 当たり判定が 44×44px 以上か（見た目の大きさとは別に確保する） |
| 4 | 読み込み中 | 押したあとに無反応の時間が無いか。何をしているかが分かるか |
| 5 | 結果が0件 | 行き止まりにせず、次の一手（条件を外す・別の探し方）を出しているか |
| 6 | エラー | 原因と、使う人ができる回復の手段を言っているか。入力した値を消していないか |
| 7 | 無効 | 押せない理由が分かるか。理由の無いグレーアウトは致命 |
| 8 | 最初の空 | まだ何も無い状態で、最初の一歩を案内しているか |
| 9 | 入力中 | 打っている間に、合っているかが分かるか |
| 10 | フォーカス | 見えるフォーカスの表示があるか |
| 11 | hover | hover にしか出ない情報が無いか（タッチでは出ない） |
| 12 | 支援技術 | 名前・役割・状態が読み上げで伝わるか。色だけで伝えていないか |

「最初の空」と「結果が0件」は別物。前者は何もしていない状態、後者はやった結果が0件の状態で、出す言葉も次の行動も違う。

境界の値も見る：0件・1件・最大件数・極端に長い名前・数字の桁あふれ・マイナス・日本語と英語の切り替え。

### 3. 一貫しているか

- 同じ意味の物が同じ見え方か（余白・角丸・影・色・大きさ）
- 同じ操作が画面ごとに違う場所に無いか
- 言葉が揺れていないか（保存と登録、削除と破棄、料金と価格）。動詞と名詞を同じ並びに混ぜていないか
- デザインシステムがあるなら、その部品を使っているか。手で似せて作った部品は、状態（hover・focus・disabled）がずれやすいので必ず比べる

### 4. 見て分かるか

- 一番目立つ物が、一番大事な物か。目立たせる手段（大きさ・太さ・色・位置）を使いすぎていないか。強調が2つ以上あると、どちらも目立たない
- まとまりが余白と配置で伝わるか。枠や線を足して整理していないか
- 情報の量が場面に合っているか。毎日使う画面は密に、たまに来る画面は説明を厚く

### 5. 壊れないか

- 幅を変えて崩れないか（スマホ・タブレット・PC）。固定幅の1枚絵になっていないか
- 320px の幅で横スクロールが出ないか。200% に拡大して読めるか
- 文字の量・言語・データの量が変わっても崩れないか

### 6. アクセシビリティ（数値で決める）

「たぶん大丈夫」と書かない。測れない物は「未計測」と書く。

| 項目 | 基準 |
|---|---|
| 本文の文字のコントラスト | 4.5:1 以上 |
| 大きな文字（24px 以上、または太字で 18.66px 以上）のコントラスト | 3:1 以上 |
| 部品の境界・アイコンのコントラスト | 3:1 以上 |
| フォーカスの表示 | 周りと 3:1 以上の差、太さ 2px 以上 |
| タッチの当たり判定 | 44×44px 以上、隣と 8px 以上離す |
| 本文 | 16px 以上、行の高さは文字の 1.5 倍以上 |
| 見出し | 階層を飛ばさない（h1 の次に h3 を置かない） |
| 動き | 5秒を超えて自動で動く物は止められる。`prefers-reduced-motion` を尊重する |
| 画像 | 意味のある画像には代替テキスト、飾りには空の代替テキスト |

数値は WCAG 2.2 の AA に沿っている。当たり判定だけは WCAG の最低値（24px）より厳しい 44px を基準にしている。指で押す画面で 24px は外しやすいからだ。

### 7. 言葉

- ボタンは動詞で、押すと何が起きるかが分かるか。画面の見出しとボタンの語がそろっているか（「アカウントを作成」の画面なら、ボタンも「アカウントを作成」）。「OK」「送信」だけで済ませていないか
- エラーは責めない。何が起きて、どうすれば進めるかを言う。システムの言葉（「レコードの挿入に失敗」）やエラーコードだけを出さない
- 説明文は読まれない前提で書く。読まなくても操作を終えられるか。長い説明で設計の穴を埋めていないか
- 入力欄の名前を、入力欄の中の薄い文字（placeholder）だけで示していないか。打ち始めると消えて、何の欄か分からなくなる
- 条件を注釈（※）に逃がしていないか。大事な条件は本文に書く
- 処理の都合（スキップした件数・内部の状態）を、使う人向けの字として出していないか

書いた文は4回読む。目的を果たしているか → 削れるか → 声に出して自然か → 誤読の余地が無いか。

### 8. 原則が破れていないか

原則の名前を挙げて終わりにしない。「どこで、どう破れているか」を書く。

| 原則 | 破れているときの見え方 |
|---|---|
| 今の状態が見える | 押したあと何も変わらない。保存できたか分からない |
| 使う人の言葉と順番 | システムの用語が出る。並び順が実務と違う |
| 出口と取り消し | 閉じられないモーダル。Undo が無い |
| 一貫性 | 同じ語が別の意味で使われている。同じ操作の場所が画面ごとに違う |
| 誤りの予防 | エラー文は丁寧だが、誤りやすい作りのまま |
| 覚えさせない | 前の画面の値を覚えて打たせる。候補も履歴も出ない |
| 慣れた人の近道 | 繰り返す操作が毎回フルの手順 |
| 余計な物が無い | 意図の無い装飾・線・色がある |
| 誤りからの回復 | 原因だけ言って次の手が無い |
| 助けが届く | 説明を読まないと使えない。ヘルプが網羅的すぎて場面に合わない |

上の10項目は Jakob Nielsen のユーザビリティの10原則に沿っている。加えて次の4つを見る。

- 押した結果がすぐ返るか。返りが 400ms を超えるなら、待っていることを示すか、先に画面を変えておく（楽観的更新）
- 「許可を求める」設計になっていないか。確認ダイアログを重ねるより、実行させて取り消せるようにする方が、使う人の流れを止めない
- 使う人が誤ったとき、「使う人の誤り」で片づけていないか。誤りやすい作りを直すのが先
- 最悪の瞬間（エラー・長い待ち・行き止まり）を残したまま、成功の演出を足していないか

### 9. AI が結果を作る画面なら

次の4つが欠けると、結果を信じてもらえない。

- **出所**：何を根拠にしたかを、結果の横で示しているか
- **確かさ**：自信が低いときにそれが分かるか。断定で書いていないか
- **生成中**：待ち時間が読めないので、何をしているかを段階で出しているか。途中で止められるか
- **直し**：全部を作り直すしか無い作りになっていないか。一部だけ直せるか、手で直せるか

AI が代わりに実行する画面（エージェント）では、実行の前に「何をするつもりか」を見せて確認を取っているか。AI が失敗したとき、手作業で同じことを終えられる道が残っているか。

### 10. デザインを再現した物なら（Figma・URL・スクショ → コード）

- 元と並べて、同じ幅で見比べたか。差を数字（ピクセルの一致率など）で出せるなら出す
- 見た目だけ合わせた1枚絵になっていないか。納品物は、幅に合わせて組み変わる本物の画面

## 出力の形

```
狙い：<この画面で、誰が、何を終えられたら成功か>
見た物：<描画して見た／コードから読んだ／スクショを見た>

致命（出す前に直す）
- <どこ> — <誰がどう困るか> — <どう直すか>

改善（次に直す）
- <どこ> — <誰がどう困るか> — <どう直すか>

好み（直さなくても成立する）
- <どこ> — <理由>

未確認
- <測れなかった項目と理由>
```

コードを直す提案は、変更の前後を表にする。

| 前 | 後 | 理由 |
|---|---|---|
| `transition: all 300ms` | `transition: transform 200ms ease-out` | 変える物を名指しする。`all` は意図しない値まで動かす |

## 避けること

- 原則の名前だけを並べる（「Hick の法則に反する」で終わる）
- 正常な状態のスクショだけを見て合格にする
- 測っていないコントラストを「問題なし」と書く
- 欠陥の数を減らすために、致命を改善に下げる
- 頼まれていない作り直しの全案を出す。直し方は欠陥ごとに最小の手から書く
